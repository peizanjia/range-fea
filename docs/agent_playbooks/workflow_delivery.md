# 全工作流开发 Agent 续作指南

更新：2026-10-08。适用：在本仓库继续实现 WF 交付计划的开发 Agent。本文提供读取/实施/验收方法，不是产品大模型可调用的工具目录。当前用户任务决定本次工作范围；任务标记为 eligible 不自行扩大授权。已有授权范围内的实现、修复、验证和本地提交按会话约定连续完成。

## 1. 先读什么

从实际 checkout 根目录开始，按顺序读取：

1. 当前用户要求和适用的 `AGENTS.md`/技能；用户指令优先，个人配置保持原样。
2. `HANDOFF.md` 顶部：当前分支/断点、最近工作、证据、下一步和环境限制。
3. `docs/DEVELOPMENT_PLAN.md` 与 `docs/workflow_delivery_plan.json`：阶段基线、状态和依赖。
4. `docs/WORKFLOW_DELIVERY_PLAN.md` 的所选 WF 节、共同契约/门槛及有关验收 ID。
5. 当前源码、测试和当前产品操作手册：`AGENT_OPERATIONS.md`、`WORKFLOW_SDK.md`、`EXTENSION_SDK.md`。主题 playbook 是导览，不替代能力查询或代码事实。

先执行只读检查：

```powershell
git status --short
git log -3 --oneline
git submodule status
python scripts/ci/verify_workflow_plan.py
python scripts/ci/verify_workflow_plan.py --next --json
```

命令从仓库根运行。历史 baseline 是追溯起点，不是 reset/checkout 目标；后续有效提交可以在它之后。确认未提交改动的所有者，保留用户改动，不能为了得到 clean 状态清理用户文件。

## 2. 如何选择工作

- 校验失败时先修复计划结构、缺失引用或状态矛盾，不执行未经过依赖检查的功能任务。
- 有 `in_progress` 时先读取其交接，核对实际代码/证据后续作；没有进行中任务时选择 `--next` 返回的首个 eligible。当前初始推荐为 WF-01。
- 写入 `in_progress` 前依赖必须完成；独立资料准备可记录在交接中，不把未满足依赖的任务标成正在实施。
- JSON 是状态/依赖的唯一来源，详细 MD 是验收规则的来源。主计划、playbook 和交接不再维护另一份相同状态表。
- `statusReason` 记录阻塞或当前进展摘要；`blocked` 必须有具体条件、受影响条款和解除方法。时间过去、预算减少或“预计应通过”不能成为 `done` 依据。
- 可并行的工作先划定文件所有权，避免两个实现 Agent 编辑同一 GUI/runner/service 文件。根 Agent 负责架构、接口、共享状态与集成；按当前用户配置使用子代理。

不要把当前闭环误读为未交付：模态/Undo/Redo、求解快照分离、受限控制/续算/曲线、私有 Python、统计扩展候选/验证/激活/回退已有基线。也不要从这些基线推断当前文档通用控制、任意扩展或中断恢复已可用。

## 3. 每个任务怎么实施

为所选任务建立临时证据目录 `build/audit-YYYYMMDD/WF-NN/`；原始日志、调试脚本、测试模型和截图放这里。先将验收条款与现有入口/测试对应，列出待增加的 schema/能力和明确拒绝范围，再开始修改。

建议增量顺序：

1. 最小可运行契约与确定性 host/service 行为，包括非法请求和失败保护。
2. 原生/进程适配与真实支持模型，固定来源、单位和独立参考。
3. GUI/CLI/SDK 接线，再向产品 Agent 能力目录开放；模型不能通过 UI 文本绕过 host 校验。
4. 正常流程、冲突/取消/故障测试；实现与验证模型的全部假设记录在同一证据中。
5. 更新当前操作手册/schema/示例，独立审查、修复、回归及本地提交。

接口名称在代码/schema 落地且 capability 发布前都属于目标设计。每次调用产品操作先查询实际能力；开发计划中的 `analysis.run`、`control.parameters.*` 等名称不能直接作为现有 RPC 发送。

保持 Qt 对象/文档操作线程归属、输入快照、结果版本验证和 accepted-step 事务；不要通过快捷调用旧控件/私有成员绕过统一路径。遇到旧入口未完成版本通知时缩小可写能力并记录后续迁移，而不是宣称全模型可安全写入。

## 4. 怎样验收

每个验收条款填写实际观察：支持场景、拒绝场景、输入/单位/版本、运行命令、输出工件、业务/数值门槛与结论。数值门槛在运行前冻结，不用观察结果反向改门槛。

必要检查按改动范围选择：

| 变化 | 验证 |
| --- | --- |
| 文档/状态/API | 正常/非法参数、过期目标、重复请求、批准范围、Undo/Redo、模型关闭、真实 GUI 和进程契约 |
| 求解/控制/恢复 | 独立数值参考、接受/失败回滚、连续/分段、中断/恢复、控制器/环境/工件篡改 |
| 对话/界面 | 真实控件、异步迟到/同步重入、输入/焦点/滚动、取消/接替、原生窗口和目标显示范围 |
| 扩展/环境 | 宿主独立基准、哈希绑定、固定旧版本、失败/回退、随包解释器和已声明隔离正反例 |
| 规划/文档工具 | 规划校验、文档引用、下一任务、状态/证据反例；不借用旧功能测试宣称新功能完成 |

集成里程碑完成时使用实际已配置的构建目录。当前可复用的 Release 命令：

```powershell
cmake --build build/vs2026 --config Release --parallel 4
python scripts/ci/verify_required_ctest.py --build-dir build/vs2026 --configuration Release --manifest scripts/ci/required-ctest-tests.json
ctest --test-dir build/vs2026 -C Release --output-on-failure
```

分别保留退出码和日志；前一步失败先定位，不能把后一步的退出码当成整个流程通过。共享 build 目录的构建/测试/安装串行执行。新必跑测试同时注册 CMake 和 manifest；只注册名字而未运行不算验收。

规划工具可独立验证：

```powershell
python -m unittest discover -s scripts/ci -p 'test_*.py'
python scripts/ci/verify_workflow_plan.py --next --json
git diff --check
```

远程模型、原生窗口、安装私有解释器、干净外部 Windows、硬件验收分别记证据。当前 `.env.local` 等本地凭据只通过既有授权的加载入口使用，不打印/导出或写入 JSON/MD/日志；QtTest 不使用 `-vs`。凭据缺失时完成独立本地工作并记录真实供应商未验收，不把模拟回复当实际调用。

## 5. 状态与证据怎么记录

状态转移：`planned → in_progress → done`；依赖满足后的任务可因具体外部/实现阻塞进入 `blocked`，解除并核对后回到 `in_progress`。工作被中断但仍可续作时保留 `in_progress` 并填写交接，不冒充完成。

`evidence` 按实际发生顺序追加，不删除失败历史。字段如下：

| 字段 | 内容 |
| --- | --- |
| acceptanceId | 本任务确切验收 ID，如 WF-01-A01 |
| outcome | pass / fail / skipped / unverified；后两项不算完成 |
| artifactPath | 仓库内的稳定验收结论或本机日志路径；不能引用凭据/用户配置 |
| commit | 实际对应代码的完整提交 SHA；核对所属根仓库/子模块，并在结论中列其关联版本 |
| notes | 实际命令、环境/模型、门槛、结果和原始日志位置的简短摘要 |

同一条款的最新证据决定当前结论；先 pass 后 fail 不能保留 `done`。全部条款通过、依赖已完成、独立审查闭合后才标记 `done`。若某条款范围改变，先记录理由/用户任务依据、影响和新旧验收映射，再更新规则与清单，不删除失败条件制造通过。

先提交实现代码以确定被测 commit，再将验收结论/状态加入收尾提交；允许在代码提交之前完成实际测试，证据必须最终对应同一代码内容。规划工具只检查结构和元数据；它不能证明提交存在、日志真实或算法正确，开发 Agent 须核对 Git、测试输出和独立审查。

跨机器可读取的长期结论放主题验收文档；原始 `build/` 日志保持本机忽略，是否可取得如实标记。不要把大工件、原始模型、供应商回复或调试日志全量加入仓库。

## 6. 中断后如何交接

在 `HANDOFF.md` 顶部记录当前任务并保持自包含：

```text
日期 / WF 任务 / 当前状态及原因
根分支与 SHA / 子模块 SHA / 未提交文件及所有者
已经完成的条款与证据；未通过条款的实际错误
最后实际执行命令 / 退出码 / 日志或截图位置
仍在运行的构建、任务或进程；其归属与核对方法
未完成操作的结果：已提交、未提交或未知；恢复时先查询核对
下一步第一条具体命令、需要读取的文件/函数和预期观察
外部环境/凭据/权限条件；哪些检查未执行
```

恢复时先核对当前 Git/源工件/运行任务，而不是照抄交接重发副作用操作。未知执行结果查询 operation/job/发布记录；中断计算只有通过实际检查点资格校验后才能续算。发现用户的新改动时保护其内容并重新分析相关版本。

## 7. 整理退出

1. 再运行规划校验与必要检查；确保所写状态、证据、接口文档和实际代码一致。
2. `HANDOFF.md` 更新当前断点；`DEVELOPMENT_LOG.md` 追加关键决策/失败/修复/验收；主题说明更新入口，不重复复制完整任务表。
3. 审查 Git diff 和待提交文件，排除 `.agents/`、`.codex/`、`AGENTS.md`、凭据及临时 build 工件。
4. 子模块先提交、根再提交；遵守用户既有本地提交约定，不自动推送。
5. 最终报告具体交付、验证及版本边界、实际可用入口和剩余条款。下一 Agent 能据交接和 `--next` 直接继续。
