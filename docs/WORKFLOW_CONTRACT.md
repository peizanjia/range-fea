# GUI、Agent 与扩展工作流契约

状态：2026-10-03 工作流设计与分阶段交付契约。断点收尾已完成；用户随后要求详细规划实时 GUI Agent 与自动二次开发，本次只完善设计，不启动功能开发。下列条目只有在对应实现、测试和交接证据齐备后才算交付。Stage 10C、11、12 保留为后续计划，不能将本文设计描述当作已实现。实际证据见 `../HANDOFF.md`，既有数值支持范围不因此扩大。第 7–18 节为这次补充的目标设计；新增接口名和类名均为提案。

## 1. 操作链与模块边界

工作流顺序为模型快照 → 分析/控制配置 → 预览 → 执行 → 接受结果 → 对照/报告；长任务具有排队、运行、成功、失败和取消状态。先以已验证四杆算例完成整条路径，再扩展已有梁功能。

- `range-application-lib` 继续拥有原生模型配置的校验与候选事务；现有 `range.application/v1` 保持兼容。
- 新工作流服务提供版本化 JSON 查询、命令目录、预览与任务接口。GUI、Agent 与 Python SDK 调用同一服务，不各自实现参数校验、文件发布或求解命令拼接。
- GUI 保持现有模型、求解和非结构功能，增量加入工作流/Agent 面板及上下文桥接；长任务不得阻塞 GUI 事件循环。
- Agent 查询当前能力与上下文，再提出结构化调用。模型回复是不可信输入，必须经过严格 schema、目录、版本和资源限制校验。
- 逐时间步控制仍使用现有 NDJSON v1/v2；工作流协议负责启动、管理和解释计算，不进入有限元 trial 或线性求解器内迭代。

## 2. 标准接口必须表达的语义

每个接口声明协议版本、操作 ID、精确参数字段、单位、只读/修改属性、前置条件、输出及错误码。未知操作、未知字段、非法数值和过期模型必须明确拒绝。

模型身份、单调会话 revision 和文件 SHA256 各有职责：身份绑定当前会话；revision 绑定编辑顺序；SHA256 绑定实际文件内容。关闭/重新载入后旧请求失效；Undo/Redo 产生新版本，不复用旧批准。

修改流程必须先生成规范化预览与摘要，批准绑定具体内容、来源模型和版本；执行时再次校验。Agent 可提出预览，不能通过回复字段自行生成批准。宿主 GUI 的明确批准操作与 Agent 工具目录分离。CLI/SDK 的宿主可在明确授权的批处理范围内批准；这不是远程认证或多用户权限系统。

重复请求不能重复启动任务或发布输出。修改中的模型不能同时用于配置提交；长任务使用不可变输入快照。当前实现运行/排队时禁止配置修改；后续完成输入快照与编辑文档分离并验收后，才允许编辑供下一次任务使用的文档，不能直接删除忙状态检查。取消或失败可以保留诊断和部分中间文件，但不发布可被误认为成功的新结果。

## 3. 审计与发布

预览、拒绝、批准、接受、开始运行、失败/取消、文件发布分别记录。记录关联 actor、命令摘要、前后 revision、run ID 及实际工件路径/SHA256；不得记录 API 凭据。尽可能沿用 `InteractionRecord v1`，额外索引作为版本化存储元数据。

先构造候选并确认审计可写，再提交修改；磁盘状态采用单文件原子发布或明确的恢复协议。日志写失败不能静默报告操作已完整成功。模型文件、任务状态和审计若不是一个磁盘原子事务，必须定义并测试中断恢复，不能只凭内存回滚推论。

## 4. Agent 工作流

Stage 11A：当前模型/能力/任务/结果查询，诊断解释，修改预览。Stage 11B：宿主批准后执行、有限步骤/时间预算、取消和失败报告。现有多供应商 `RAgent` 作为可替换的文本推理端，结构化工具桥接负责执行；测试使用确定性模拟回复，实际远程模型验证单独记录。

侧栏展示当前工作阶段、模型/运行来源、对话、待执行内容、批准/拒绝按钮和任务结果。上下文只发送完成任务所需的配置、目录与摘要；完整大向量、秘密信息和无关文件不自动加入。

## 5. 版本化 SDK 与受控扩展

Stage 12A 先提供进程外 Python 客户端、握手/能力发现、错误映射、示例与契约测试。不得把内部 C++ 头文件或未设计 ABI 宣布为稳定插件 SDK。

Stage 12B 首个扩展必须有实际用途并通过正式入口运行。流程为能力缺口 → 扩展需求/输入输出 → 生成候选源码和测试 → 隔离目录校验 → 展示源码差异与验证结果 → 宿主批准固定内容哈希 → 注册/进程外执行 → 结果及审计。失败候选可归档/清理，不能覆盖已激活版本。

扩展清单至少声明 ID、版本、SDK 协议、扩展类型、输入输出和源码/测试哈希。批准和测试结论都绑定相同内容；源码变更后必须重新验证批准。执行有超时、输出大小和并发限制，使用可控 argv，不拼接 shell 命令。进程隔离和临时目录不等于操作系统安全沙箱；任意生成代码执行前必须由宿主明确授权，不在生产 GUI 进程中动态加载。

## 6. 验收顺序

1. 10A：真实 GUI Session 基线操作；模型生命周期与审计；变更后重跑窗口/保存重开/旧请求拒绝。
2. 10B：四杆配置、实际 FE 主动/被动对照及独立参考；同一流程的续算、取消和失败恢复。
3. 10C/11A：工作流面板和只读 Agent 可并行集成；11B 在批准、版本和审计贯通后验收。
4. 12A：干净进程 SDK 客户端使用相同能力目录和契约；12B 验证一个从生成到激活使用的实际扩展以及失败/篡改/超时反例。
5. 全目标 Release、必跑测试清单、完整 CTest、安装树及独立审查；干净 Windows、远程 CI、远程模型或硬件未测项保持独立声明。

每个里程碑更新开发计划、交接和提交；不能用模拟 Agent 回复代替真实工具执行，也不能用单元测试代替实际 FE 或完整 GUI 链路。

## 7. 产品目标与当前缺口

目标体验：用户在现有窗口选择模型，Agent 读取当前已接受状态，解释问题，给出有来源的建议；用户直接要求执行或在允许范围内批准后，同一应用服务修改模型，参数、模型树、结果及操作记录同步更新。计算、网络请求、环境准备和扩展测试在后台进行。正常使用不要求保存后重开模型，也不要求重启主程序。

当前基线为根提交 `39e1d65`：

| 层 | 当前已有 | 仍需建设 |
| --- | --- | --- |
| 模型操作 | `RModelCommandSession` 模态校验/会话；`ModelCommandHost` 接 GUI Undo/Redo、逻辑 UUID 和修改代次 | 全局文档版本、统一命令目录及读模型；旧入口变更完整覆盖 |
| 工作流 | `WorkflowService` 固定四杆/梁模板、预览/批准、作业/工件/恢复；`WorkflowClient` 进程客户端 | 与当前打开模型的上下文桥接、事件订阅、GUI 面板；受支持用户模型快照导入 |
| 大模型 | `RAgent`、`RAiChatWidget` 有文本对话、供应商设置、请求取消和会话 | 结构化工具回合、任务状态机、上下文服务、预算与执行策略 |
| 扩展 | 工作流预留注册位置；未启用的本地草稿 | 稳定 SDK、打包运行时、声明式界面、版本激活和真实自动开发闭环 |

现有 `range.application/v1` 的 revision 属于单个编辑会话；现有 `range.workflow/v1` 的 revision 属于独立模板工作区。不能把二者直接作为同一个 GUI 文档版本。97 项历史本地回归证据不覆盖本节未来功能。

本轮只读核查还发现需要优先收敛的旧路径：`ModelCommandHost::query()` 在任一管理器忙时全局拒绝查询；`SolverTask::perform()` 持有活 `Session` 的 `Model&` 并在求解结束后回写；部分旧控件在外部求解期间仍可编辑。`Session` 修改代次依赖固定信号集合，例如网格输入对话框存在直接修改后提交任务的路径。当前模态服务的保护不能外推为全应用并发保护。10C.1 第一批应先建立旧入口清单和一致的临时冲突策略，再推进 10C.3 的快照拆分；本轮不改这些实现。

### 7.1 “不中断”的具体承诺

| 操作 | 目标行为 | 生效范围 |
| --- | --- | --- |
| 查询、解释、选中/高亮、切换图表 | 主窗口持续可操作；必要时仅更新相关视图 | 当前界面 |
| 修改分析/控制/模型配置 | 校验通过后更新当前文档，可撤销；已过期的预览重算 | 当前编辑版本 |
| 计算期间修改参数 | 已运行任务继续；修改进入下一次输入；界面显示“运行使用版本 A，当前编辑版本 B” | 新运行或明确的新分支 |
| 增加/更新 Python 后处理、报告、参数工具 | 后台准备新版本，成功激活后出现菜单/面板；旧任务仍使用旧版本 | 新调用 |
| 更换扩展依赖/解释器 | 创建新环境并切换新调用，待旧任务结束再清理旧环境 | 新扩展进程 |
| 修改单元内核、主程序 C++/Qt 或原生库 | 开发与验证可在后台；通过新求解进程版本供新任务使用；主程序自身更新走正常升级 | 相应新进程/下一次主程序启动 |

实时显示是对已接受操作及时反馈，不是每个输入字符都进入模型，也不是在求解器一个时间步的中间改写其矩阵。在线控制器参数切换只能另立 accepted-step 命令及稳定性/重启一致性验收，工作流 Agent 不进入控制采样环。

## 8. 本地架构与唯一状态来源

```text
GUI 菜单/表单 ───────┐
Agent 编排器 ────────┼→ 本地应用入口 → 命令/查询注册表 → 文档、作业、工件
Python SDK / MCP ───┘          │                       │
                              └→ 操作记录/变更事件 ←───┘
                                        │
                             GUI 视图更新 + Agent 上下文失效

Agent 编排器 → 供应商适配器 → 云端/本地通用大模型
作业管理器 → FE 进程 / Python 计算进程 / 扩展工作进程
```

部署先采用一个桌面宿主及其受管子进程；不为这些逻辑模块引入一组微服务。

1. **文档宿主**：现有 GUI `Session` 持有打开模型的接受态；扩展 `ModelCommandHost`，以稳定身份查询模型。Agent、Python 和网络线程不持有 `Model*` 或 QWidget 指针。无 GUI 的 CLI 可以持有独立文档宿主，但不能与 GUI 同时认领同一打开文档的写入权。
2. **命令/查询注册表**：建议在 `range-application-lib` 增加 GUI 无关的描述、校验和候选计算；GUI 宿主适配器负责线程、选择、Undo 和通知。已有模态、工作流服务仍负责各自业务规则，不在 Agent 中复制。
3. **作业管理**：保留 `range-workflow` 执行逻辑；输入由宿主生成不可变快照并注册为工件。把当前固定模板工作区和未来打开文档映射分开，服务不再通过改写 GUI 的原模型文件完成同步。
4. **上下文服务**：建议 `GuiContextBridge` 在拥有线程取得轻量快照；`ContextBuilder` 选取模型事实、能力、结果摘要及文档片段。窗口改变只使关联上下文过期，不强制取消整个对话。
5. **Agent 编排器**：建议 `AgentTaskRunner` 和 `AgentToolGateway` 独立于供应商；持有计划、工具请求、预算、待批准动作及证据。初版一个编排器即可，内部多 Agent 不作为产品前置条件。
6. **扩展宿主**：建议 `ExtensionManager`、`RuntimeManager` 管理不可变版本目录、独立进程和输入输出；GUI 使用宿主实现的控件渲染扩展描述。

### 8.1 身份与版本

| 标识 | 职责 |
| --- | --- |
| `projectId` / `documentId` | 项目和逻辑文档身份；不能用模型列表下标代替 |
| `sessionEpoch` | 本次打开/重载代次；旧窗口、旧请求或旧批准不跨代次复用 |
| `documentRevision` | 文档接受操作的单调版本；Undo/Redo 也产生新版本 |
| `selectionRevision` | 当前选择/焦点版本；改变选择不会使固定目标文档的合法命令无故失效 |
| `capabilityRevision` | 已安装、已激活及当前适用的命令能力目录版本 |
| `snapshotId` / `sha256` | 输入、结果、代码、环境等不可变内容的身份及真实字节摘要 |
| `operationId` / `jobId` / `eventSeq` | 已接受操作、后台计算、变更事件的关联与去重 |

文档 revision、输入工件 SHA256、Qt 对象地址和当前选中项是不同概念。初期采用整个文档冲突检查；只有测得过度冲突后才引入组件版本，避免一开始维护复杂依赖图。

### 8.2 GUI 当前输入与旧入口迁移

- 上下文分别报告已接受值、尚未提交的表单草稿、未保存到原文件的文档修改。Agent 不把屏幕正在输入的半个数字当作有效参数。
- Agent 提案固定目标文档及实体 ID；用户切换模型时，提案不会偷偷跟随选中项改变目标。
- 手工编辑与 Agent 修改经过同一提交入口。发生重叠修改时显示具体冲突，重新查询和预览，不自动覆盖用户输入；没有冲突的视图操作可以继续。
- 按“模态 → 工作流配置 → 支持的控制配置 → 材料/边界/载荷 → 几何/网格”的工作流顺序迁移。每一类记录 GUI/CLI/Agent/SDK 入口覆盖情况。
- 暂未迁移的旧命令必须通过 `Session` 的统一修改通知使版本失效；若无法证明某路径通知完整，对应能力不向 Agent 开放写入。不能以控件刷新信号代替模型接受事件。

## 9. Agent 标准工作流

```text
读取当前状态 → 明确目标 → 检查能力/缺失条件 → 工具分析
     → 给出建议与证据 → 生成修改预览 → 宿主判断授权范围
     → 提交或启动作业 → 订阅进度 → 查询验证 → 界面呈现与总结
```

| 步骤 | 必需内容 | 完成条件 |
| --- | --- | --- |
| 读取 | 项目/文档/选择、revision、分析类型、任务、有效结果、草稿和安装能力 | 形成带版本的 ContextSnapshot |
| 分析 | 确定性模型检查、数值分析工具、相关说明；只获取所需数据 | 结论可指向模型字段、诊断或结果工件 |
| 建议 | 问题、证据、假设、建议动作、预计影响、验证方式 | 区分已证实问题与待验证判断；未知算量不编造精确秒数 |
| 预览 | 规范化参数、目标、差异、单位、失效结果、Undo 和资源要求 | 服务生成 previewId/digest；自然语言回答不能代替预览 |
| 授权 | 用户当前明确请求或先前授予的范围；超出范围再确认 | 宿主生成许可，LLM 不掌握批准工具或凭据 |
| 执行 | 再次校验版本、工件/代码哈希、权限、任务前置条件 | 返回 operationId，长任务返回 jobId；不凭模型回复标记成功 |
| 验证 | 重新查询接受态、检查任务终态及数值/业务验收指标 | 修改、计算完成、结果合格分别可见 |
| 总结 | 做了什么、改变哪些对象、依据、结果、仍未完成内容 | 绑定来源版本，提供撤销/查看结果/继续操作入口 |

建议以 `Recommendation {evidenceRefs, assumptions, proposedCommands, affectedObjects, expectedEffect, verificationPlan}` 保存可见决策记录，不记录模型隐藏推理。分析需要实际求解时形成后台作业；语言模型不负责代替数值计算。

任务状态机：`observing → analyzing → proposing → awaiting_authorization → executing → verifying → completed`；允许 `failed/cancelled/interrupted`。取消模型请求、取消 Agent 后续步骤、取消 FE 作业是三个独立动作，界面应说明作用范围；停止对话不能悄悄终止用户此前启动的计算。

### 9.1 授权不应造成连续弹窗

- **建议模式**：自动查询、诊断、生成预览；模型不修改。
- **执行当前请求**：用户明确要求的可逆操作直接在该范围内执行；宿主记录请求与预览绑定，界面显示修改及撤销入口。
- **有界任务委托**：用户一次设定目标文档、允许命令、参数/资源范围、有效期与停止条件；范围内逐步执行，超出范围才暂停确认。
- 发布/覆盖外部文件、安装新依赖或首次运行生成代码采用独立授权范围；已明确批准且内容未变的动作不反复询问。授权是宿主能力，命令参数中的 `approved: true` 没有效力。
- 重试只针对可恢复条件；采用同一幂等键查询原操作，不重新生成键重复启动。版本冲突需要重新预览；未知执行结果先查询，不能猜测失败后再执行。

## 10. 统一接口设计

### 10.1 协议与传输

新增聚合入口建议使用 `range.host/v1`，将上下文、文档、任务、事件及扩展映射到现有服务。它是薄适配层，不取代 `range.application/v1`、`range.workflow/v1` 的实现。现有协议严格拒绝多余字段，不能直接给旧封套加入 GUI 字段而继续声称兼容。

首版优先使用宿主启动子进程的标准输入/输出或本机命名管道；stdout 只含协议，stderr 为诊断。请求响应和事件必须可区分，支持 requestId 多路关联、取消、消息大小/并发/超时上限和有界事件队列。握手协商协议、能力、事件支持、运行时和包版本。

宿主绑定连接身份、项目和允许操作；批准通道与 Agent/扩展工具通道分开。面向第三方的本机通道需要用户 ACL、会话连接凭据及明确的目标实例，不能只凭知道管道名便允许写入。现有 `host.approve` 的可信调用者假设不等同于这些认证措施已经实现。首版不开放远程监听。

| 接口族（拟定） | 操作示例 | 内容 |
| --- | --- | --- |
| 能力 | `capabilities.query`, `schema.get` | 可用命令、参数/结果 schema、适用范围、不可用原因 |
| 当前状态 | `context.query`, `document.query`, `selection.query` | 同一快照的模型/任务/选择/草稿摘要；按需分页读取 |
| 分析 | `diagnostics.run`, `analysis.submit` | 检查与计算；长任务返回 jobId |
| 修改 | `command.preview`, `command.execute`, `operation.query` | 固定差异、宿主授权、版本校验、幂等确认 |
| 撤销 | `document.undo`, `document.redo` | 经过同一文档历史；不能用恢复旧文件冒充撤销 |
| 任务 | `jobs.query`, `job.cancel`, `job.resume` | 状态与停止；不兼容续算必须新建任务 |
| 结果 | `results.query`, `artifact.read` | 来源、单位、类型、哈希、有效性及分片数据 |
| 界面 | `view.select`, `view.highlight`, `view.showResult` | 受限可见动作，不把任意 Qt 方法暴露成工具 |
| 更新 | `events.subscribe`, `events.read` | 文档/任务/结果/能力变化；支持游标及过期重同步 |
| 文档 | `knowledge.search`, `knowledge.read` | 兼容当前安装版本的说明、示例、公式/假设和 SDK |
| 扩展 | `extension.propose`, `extension.validate`, `extension.activate`, `extension.rollback` | 生命周期，准备/测试为作业，激活受宿主管理 |

命令描述至少包含：ID/版本、输入与输出 schema、单位与坐标约定、适用 capability、前置条件、读写对象、效果分类、运行中编辑策略、Undo/幂等属性、结果失效范围、所需权限、资源预算、文档与测试引用。JSON Schema 负责结构，求解器/应用服务仍负责物理和业务校验；schema 通过不代表模型可求解。

数值工件同时声明实体ID、坐标系/全局方向、物理量、单位、数组形状、时间基准、缺失值与有效性；局部DOF标签不能推断全局坐标轴。初版一条编辑命令只提交一个文档；批量工作流明确返回逐项状态。跨模型整体事务只有实现统一候选/回滚并通过故障测试后才能声明，当前“先全检再提交”不能视为该保证。

示意请求（新协议提案，不能直接发送给现有工作流服务）：

```json
{
  "apiVersion": "range.host/v1",
  "requestId": "req-104",
  "operation": "command.preview",
  "parameters": {
    "target": {"documentId": "doc-7", "sessionEpoch": "open-3"},
    "expectedDocumentRevision": 42,
    "command": "analysis.modal.configure",
    "commandVersion": 1,
    "arguments": {"method": "multiple", "iterations": 100, "modes": 6, "tolerance": 1e-9, "unit": "1"}
  }
}
```

预览返回固定目标、规范参数、前后差异、readSet、影响/警告、预计失效结果、previewId 和 digest。执行只引用已保存预览与幂等键；授权由可信连接上下文附加，不把批准令牌送进大模型上下文。

```json
{
  "apiVersion": "range.host/v1",
  "requestId": "req-105",
  "status": "accepted",
  "code": "OK",
  "result": {
    "operationId": "op-58",
    "documentId": "doc-7",
    "beforeRevision": 42,
    "afterRevision": 43,
    "changedPaths": ["analysis.modal"],
    "invalidatedResultIds": ["result-9"],
    "undoGroupId": "undo-58",
    "eventSeq": 281,
    "persistence": "recovery_checkpointed",
    "fileSaveRequired": true
  }
}
```

`accepted` 表示此修改已经提交；`queued/running/succeeded` 是作业状态；`validationPassed` 是结果校核结论。三者不得共用一个含糊的“完成”。错误统一包含 code、用户消息、字段/对象定位、是否可重试及建议恢复操作，例如 `STALE_REVISION`、`DRAFT_CONFLICT`、`MODEL_BUSY`、`UNSUPPORTED_CAPABILITY`、`AUTHORIZATION_REQUIRED`、`INVALID_RESULT`。不把进程内部路径或堆栈默认塞给最终用户。

### 10.2 事件与可靠恢复

变更事件至少包含 `eventId, eventSeq, type, documentId/jobId, operationId, beforeRevision, afterRevision, changedPaths, artifactRefs`。文档提交事件可靠保留；高频进度允许合并，完成/失败/取消终态不能丢失。GUI 按 revision/eventSeq 去重，事件缺口时重新取得完整快照。

先实现宿主拥有的有序事件与快照重同步，再补齐持久操作账本和恢复检查点。目标采用单个本地项目元数据存储（可用 SQLite 管理操作/事件索引），大模型和结果工件保留为不可变文件。文件发布与元数据提交是两个边界：先写并校验候选工件，再提交关联及待发送事件；中断时按 operationId 核对，未被引用的候选可回收。不能因采用 SQLite 就宣称模型文件也处于同一事务。

只有模型候选和操作账本恢复条件成立，才返回上例的 `recovery_checkpointed`；否则明确 `memory_only` 并保留未保存状态。Agent 受监督写入上线前须完成接受操作、Undo 分组、崩溃恢复、重复请求和界面通知的一致性故障测试。Undo 与运行/文件发布分开：撤销模型编辑不删除已经完成的结果，也不自动撤回外部文件。

## 11. GUI 实时一致性与并发

提交链：目标版本检查 → 候选校验/准备 → 提交接受态及历史 → 更新版本和操作记录 → 发布变更事件 → 更新相关视图。只有接受态变化才发正式成功通知；预览使用可清除的独立覆盖层。

- QWidget 和实时文档提交留在拥有线程；网络、FE、Python、哈希、重网格和大结果处理移至后台。大模型复制/序列化也不能长时间占用 GUI 线程。
- 后台只读取不可变快照，返回候选或工件；GUI 提交前复核 revision。先做短而有界的提交，测得瓶颈后才引入更细粒度结构共享。
- 默认异步 queued 调用并带完成回调；避免同线程 BlockingQueuedConnection。网络断开或扩展退出只影响对应任务，主窗口仍可操作。
- 文档事件驱动属性表、模型树、脏标记、Undo/Redo、结果有效性；涉及几何/载荷/视图数据时才更新相应视口，不全窗口反复刷新。
- 保留焦点、滚动位置、选择和未提交草稿。Agent 不主动跳走用户当前页面；提供“查看修改”定位入口。
- 求解使用提交时的 snapshotId。新修改立即显示，但运行进度固定标记旧 snapshotId；结果按原始版本登记，用户可对比或显式设为当前显示。
- 第一版可使用全局作业互斥；放宽为按文档资源锁之前，必须逐一确认旧求解/保存/重载路径没有访问活文档。支持运行中编辑依赖此迁移，不能单独取消 `hasRunningJobs()` 判断。

拟定验收目标：参考硬件及代表模型明确后，普通参数提交至相关界面更新 p95 ≤ 200 ms；长任务接收反馈 ≤ 300 ms；进度刷新约 5–10 Hz；测试中能持续旋转视图、编辑其他文档和取消任务。这些是待测目标，不是当前性能证据，也不要求大型重网格在 200 ms 内完成。

### 11.1 界面布局与日常使用

- 主工作区保留模型树、视口、属性和结果。Agent作为可收起侧栏，不接管整个程序；未配置模型服务或网络离线时，手动工作流仍可用。
- 侧栏顶部固定显示当前目标模型、是否有未提交修改、当前任务；中部用“发现/建议/修改预览/执行结果”卡片；底部为输入和停止按钮。技术revision/哈希可展开查看，默认展示用户可理解的模型名和版本来源。
- 底部任务区显示FE、Agent、扩展准备各自的状态和取消入口；失败可定位参数或重试，不能只显示一段原始异常文本。
- 预览卡片列出原值→新值、影响范围、会失效的结果和验证方式；应用后变为已执行记录，附撤销和查看修改入口。
- 扩展管理页显示功能用途、版本、来源、适用数据、验证状态、启用/停用/回退。首次使用以运行示例检查环境，普通用户不需要编写脚本或维护包管理命令。

## 12. 通用大模型适配与上下文

保留 `RAgent` 已有供应商/连接设置基础，将文本传输与工具循环拆开。供应商适配器建议统一产生 `textDelta, toolCall, usage, finish, error`；它只转换模型 API 格式，不拥有 FE 写入能力。编排器采用相同工具目录，因此换模型不会改写业务规则。

每个适配器声明并实测能力：工具调用、结构化输出、流式回复、取消、上下文预算和错误映射。只有通过契约测试的适配器开放执行；文本-only 模型可继续解释与建议。不假设所有标称兼容某 API 的服务都支持相同 JSON Schema 子集；内部完整 schema 与供应商可接受的投影分开，宿主始终执行完整校验。

上下文分层：

1. 固定简短的产品角色、单位约定与执行规则。
2. 当前轻量状态、来源版本、任务目标、可用工具摘要。
3. 按需检索的命令 schema、能力约束、模块说明与示例。
4. 确定性工具计算的数值摘要/图表/诊断；大矩阵、大网格按范围读取，不全量放进 prompt。
5. 本次任务决策及已执行操作摘要；长期事实以项目元数据和日志为准，不依赖聊天记录记忆。

模型请求只发送完成任务所需数据；用户可查看“本次发送的内容”。密钥由宿主凭据层引用，扩展工作进程不继承供应商密钥。文件内容、模型标签、工具日志和外部文档作为数据，不能覆盖宿主规则或扩大权限。

MCP 可作为后续对外适配层：将注册表映射为 tools、文档/结果映射为 resources；内部版本、审批和数值校验仍由宿主负责。先打通内置侧栏，避免为了接 MCP 同时重写内部命令系统；它也不能代替供应商适配器。

## 13. 本地文档和机器契约

需要详细文档，但分工应清楚：**运行时查询提供当前事实，schema 提供可调用规则，MD 解释用途和边界，示例/测试证明这些说明可执行。** 用户不必自己编写 MD 才能使用产品；正常安装应带相应知识包。

建议源码和安装布局（均待建，不改变用户根目录 AGENTS.md）：

```text
docs/agent/                 # 架构、数据流、错误恢复、上下文规则
docs/playbooks/             # 每个完整用户任务的操作指南
schemas/host/v1/            # 请求、响应、事件和工件格式
schemas/extensions/v1/      # 扩展 manifest、GUI 贡献、输入输出
examples/sdk/              # 可运行的建模、求解、结果处理实例
src/.../tests/contracts/    # schema/示例/能力目录一致性测试
share/range/knowledge/     # 随版本安装的知识索引和文档
```

每份 playbook 包含适用 capability/版本、前置状态、输入单位/坐标、操作顺序、成功判断、失败处理、代表例子和不支持场景。数值说明还包括假设、方程、适用单元/边界和误差证据。

命令参考/参数表尽量由同一描述生成；MD 保留解释，不再手抄一份会漂移的参数约束。知识索引绑定 appBuild、SDK/schema 版本、capabilityId 和文档哈希。CI 检查断链、失效操作名、示例执行及安装包是否带齐文档。初期按 ID/关键词检索足够，规模需要时再增加语义索引。

项目的 `.range/` 元数据可保存任务目标、用户约束、操作/结果索引和 Agent 会话摘要；项目事实与用户偏好分别管理，提供查看/修改/清除入口。项目便笺只能提供背景，不授予命令或代码执行权限。

## 14. Python 运行时与软件打包

推荐自带**经过固定版本验收的私有 CPython 运行时**，通过独立 `python.exe` 进程运行；普通用户不安装 Python、不修改系统 PATH，也不向主 Qt 进程嵌入 CPython。现阶段外部 Python 入口可保留为开发者模式。

| 层 | 首选内容 | 安装方式 |
| --- | --- | --- |
| 基础运行时 | 固定 CPython、小型协议/schema/SDK 依赖 | 随软件；版本目录只读，独立更新 |
| 核心计算 | NumPy、SciPy；现有杆/梁流程必须具备 | 随核心计算组件交付；固定 Python ABI、平台和 BLAS 依赖 |
| 数据/报告 | 按场景选择 pandas、Matplotlib、SymPy 等 | 可选功能包；绘图先采用非交互后端/结构化曲线返回宿主 |
| 学习/加速 | PyTorch、GPU/CUDA、Jupyter 等 | 后续独立组件；不作为第一次启动基础依赖 |

CPython Windows embeddable 包可作为受控部署基础，但不能假定它是支持正常在线 pip 管理的完整 Python。构建阶段将已验证 wheel/依赖纳入分发；需要一般包管理的开发模式另用完整私有运行时。具体 Python 小版本在目标 Windows、NumPy/SciPy wheel、原生 DLL 和 SDK 的兼容矩阵通过后冻结，避免本设计绑定未经测试的版本。

目录按 runtimeId + 环境锁文件哈希区分；扩展使用不可变、可并存的依赖环境。准备新环境时不修改共享 NumPy/SciPy，不对活跃环境直接 pip install。相同锁文件可以复用环境，不能用版本区间相近作为兼容依据。包源、wheel 哈希、Python/平台 ABI、许可证清单和构建记录纳入发布工件。

如采用 `venv`，必须在最终路径创建或在安装时重建，不能把开发机 venv 直接复制后当作可迁移分发。受控嵌入式布局可使用固定依赖目录，但仍要独立验证其模块搜索路径、DLL加载和环境变量隔离。生成扩展与用户数据使用可写数据目录，程序安装目录保持只读。

默认只运行随包或已批准仓库中的依赖；缺包时给出功能、下载体积和依赖变更预览，由依赖管理器安装到新环境，Agent 不自行执行任意联网安装命令。离线安装使用同一 wheelhouse。安装验收包括无系统 Python、无开发 Qt、无网络、中文/空格路径、普通用户权限及核心数值参考；不能用开发机成功替代该验收。

运行时打包、依赖来源和再分发审核进入 Q3 持续质量线；本设计不作现有 Qt/TetGen 等依赖的商业授权结论。

## 15. 扩展模型、GUI 贡献与热激活

### 15.1 扩展范围

| 类型 | 首期适合的功能 | 接入方式 |
| --- | --- | --- |
| 后处理/报告 | 峰值/RMS、包络、能量对比、频谱、批量报告 | 只读结果工件 → 带单位结果/曲线/表格 |
| 参数与建模助手 | 参数扫描、受支持模型生成、批量配置 | 生成标准命令计划 → 宿主预览/执行 |
| 工作流组合 | 多方案对比、收敛研究、控制试验 | 编排现有作业，保留每个输入版本和验证结果 |
| 控制器/求解扩展 | 新控制律或新数值算法 | 先离线验证；固定版本供新的求解任务使用 |
| 新单元/材料/原生求解内核 | 核心 FE 能力 | 单独的高风险开发里程碑：理论、收敛/守恒/参考测试、构建和发布 |

二次开发可以产生前所未有的后处理算法和工作流，但只能通过已提供的数据和提交接口进入软件。新物理模型不因能够运行 Python 就自动获得 FE 支持。

### 15.2 扩展包契约

扩展 manifest 至少包含：extensionId、版本、协议/SDK范围、类型、entryPoint、输入/输出schema引用、单位/坐标约定、权限、运行时/依赖锁哈希、源码/测试哈希、GUI贡献、验证报告、资源上限。相对路径必须归属于扩展包目录；输入工件由宿主解析并提供，不能依赖任意用户路径。

GUI 贡献使用有限的声明式描述：参数表单、菜单动作、结果表格、曲线、报告、模型叠加标记。宿主生成控件并校验数据，扩展不创建 QWidget、不注入任意 QML/JS。新增需要自定义控件的需求先扩大宿主组件库，再允许扩展声明使用。

Python SDK 首版包含能力发现、项目/结果只读查询、工件分片读取、作业启动/取消及命令提案。建模工具提交 `CommandPlan`，不能拿内部模型指针或任意修改工作区文件。扩展工具返回值必须通过输出 schema、有限数/尺寸/单位检查，随后再进入结果目录或预览。

### 15.3 热激活与回滚

```text
draft → environment_ready → tested → awaiting_activation → active
                                               旧版本 → draining → retired
任一准备/测试失败 → failed；活动版本保持不变
```

新版本准备、测试和健康检查都成功后，宿主原子更新活动版本指针、增加 capabilityRevision，并通知 GUI 和 Agent 刷新目录。新调用使用新版本；运行中任务固定源码/依赖/输入哈希，继续旧进程，不在已 import 的模块上原地 reload。

回滚只切换之后的调用，不倒转已完成的数值结果或已提交文档编辑；这些用文档 Undo 或新的补偿操作处理。状态型扩展首版不支持隐式跨版本内存迁移；状态存为版本化工件，显式迁移并验证后才接续。活动任务和项目结果引用的旧版本禁止垃圾回收，引用解除后才清理。

## 16. Agent 自动二次开发标准流程

1. **确认能力缺口**：先查能力目录、已有扩展与依赖，判断是组合现有操作还是确需新功能。
2. **形成需求规格**：输入/输出、单位、支持范围、GUI呈现、失败情况、数值或业务验收阈值和资源预算。
3. **创建候选**：在独立开发目录生成源码、manifest、说明和测试；保留基础版本与差异，不覆盖活动扩展。
4. **准备环境**：依赖管理器解析固定依赖、构建新环境；依赖改变属于候选的一部分。
5. **自动校核**：语法/import、协议/类型、确定性样例、独立基准、错误/空数据、超时/崩溃和资源限制。自生成测试不能是唯一正确性证据。
6. **试运行**：在选定只读输入快照上计算，输出进入候选结果目录；并行保留旧版参考结果。
7. **展示验证结果**：用户看到新增功能、界面入口、例图/表格、适用边界、权限/依赖变化及测试结果；源码差异供展开查看。
8. **授权激活**：绑定源码、依赖、manifest、测试与验证结果哈希；任一变化都使旧验证/授权失效。
9. **即时使用**：注册后新按钮/表单/工具可见；Agent 查询新 capabilityRevision 后调用，结果回到既有结果面板。
10. **跟踪与回退**：记录调用版本、异常与用户反馈；达到错误阈值可停用新调用，保留旧版和诊断。

首个推荐扩展：对指定传感器位移/速度时程计算窗口 RMS、峰值和包络，提供时间窗参数、曲线与结果表格；用解析信号/固定小样例独立校验。随后做参数扫描/主动被动批量比较。阻尼识别、稳定性判断和新控制律需要额外假设与误差验收，不应作为最简单首例。

**执行隔离必须有可验证边界。** 独立进程、虚拟环境和 Job Object 可以帮助崩溃/资源管理，但不等于限制文件、网络和注册表访问。扩展 manifest 权限声明也不会自动施加 OS 权限。首期已审核可信扩展可在明确授权下运行；通用模型生成代码面向普通用户自动运行前，必须交付受限 OS worker（候选 AppContainer 或其他经验证的隔离后端），并测试禁止读取未授权文件、访问网络及写入安装目录。若该边界未交付，产品须保留为“受信开发者模式”，不能称为安全的任意自动扩展。此处只规划，不修改本机 Sandbox/Hyper-V/权限设置。

合计串行粗估 **15–27 人周**，不含新的 FE 单元/主程序原生热更新、任意三方包兼容或广泛硬件验收。11A 可在 10C.1 后与面板并行；Python 打包可与 11B 并行；11B 实时执行依赖 10C 的状态/事务基础；12B 依赖 SDK、扩展运行时和相应隔离/授权边界。先交付窄而完整路径，再扩大支持范围。

建议第一个端到端验收故事（运行期间编辑部分以 10C.3 验收为前提）：用户打开已支持模型 → Agent 查当前状态 → 提出并执行一次模态配置修改 → 属性栏立即更新且可 Undo → 启动作业 → 用户仍可编辑下一版 → 结果带来源显示 → Agent 引用真实结果总结。用户模型导入必须单独通过能力检查；当前模板工作流不能直接当成任意模型入口。

建议第二个故事：用户要求一个此前没有的时程统计功能 → Agent 生成并验证扩展 → 一次激活 → 当前 GUI 出现参数表单和结果图表 → 旧作业继续 → 新版故障时回退后下一调用恢复。两个故事都通过后，才宣称具备用户所要求的实时 Agent 与受控二次开发体验。

## 18. 设计取舍与外部依据

- 本地宿主是权威；大模型负责理解、建议、计划和生成候选。验证、权限、模型提交和结果发布由确定性代码执行。
- 采用统一描述加薄适配层，复用现有 C++/Python 服务；避免维护 GUI/Agent 各自的参数规则。
- 扩展采用进程外版本切换和宿主声明式 GUI；原生主程序更新保持正常发布路径。
- 文档随版本发布并可检索，机器契约和可执行例子承担准确性；不用单个超长 MD 承担全部产品逻辑。
